# 松手画面回弹与逐帧锁评估（2026-10-29）

## 已有证据

本轮离线复核了以前由用户复现时留存的光标快照、帧分类和状态记录，没有运行新的全局光标诊断。不能以这些旧记录替代当前版本在 Finder 的新实测。

旧记录中有三次同一松手起点内的明确画面回退。例如以一次松手开始为 0 ms，实际图像依次是：

| 相对时间 | 实际图像匹配 |
| --- | --- |
| 6.041 ms | 松手数组下标 1 的形状 |
| 10.004 ms | 按住末态／松手数组下标 0 的共同形状 |
| 22.319 ms | 松手数组下标 1 的形状 |
| 37.760 ms | 松手数组下标 2／3 的共同形状 |

快照中保存的 motion 始终为 release，started 未改变。这里的多个标签表示素材图片本来相同，不能仅靠图像判断到底是哪一个状态选择了它。相关时刻早于提交记录滚动缓冲区的保留范围，不能声称已将每个可见图像一一对应到某次 API 提交。

## 当前代码能保证什么

- InteractionMachine.up 仅在已有按住时建立松手阶段；重复 up 不会重新建阶段。
- SystemCursorRenderer.ReleaseClock 对同角色、尺寸和起点的索引取最大值，且松手不循环。发现已显示的后续帧时只向前接续。
- 但这是 Gallery 的提交顺序，不是屏幕的全局互斥锁。角色未知后的 passThrough、角色或尺寸改变、切换系统场景可能交还／重建呈现。
- 当前交互路径还涉及系统注册资源和非文字的 NSCursor 提交。前台应用也能重选光标；单个 Gallery 状态机无法阻止其他进程／系统的重选或已排队的呈现。

这些证据更符合光标交接、旧资源重选或提交呈现顺序的问题，而不足以断言是 Finder 本身的 bug，也不能把所有回弹都归因于重复鼠标事件。确切产生旧图像的调用方仍未确认。

## 对严格逐帧锁的判断

在 Gallery 内实现“只能第 n 帧接第 n+1 帧”可行；现有保护已经覆盖“不回退”的一部分，但允许按时间跳过过期帧。强制每帧完整等待后再前进，会在负载高时延长动画，增加新点击等待；锁到最后一帧也会延迟角色切换。停止、恢复系统指针、屏幕锁定等必须始终允许取消，不能被动画锁住。

因此，单独增加一个绝对的“播完前禁止其他内容”锁不能保证消除已观察到的系统画面回退，本轮没有将它加入正式版。

若继续实验，应分别验证：

1. 将一次手势的松手素材固定到结束，只暂缓普通角色识别；新物理 down、停用和系统场景切换仍立即抢占。这样能检验片段切换是否贡献回弹，但会暂时延迟角色响应。
2. 为松手尝试单一呈现提交路径，限制在途帧，实际图像确认后再推进，并设置有限超时；分别记录“拟显示、已提交、屏幕已看到”。当前确认机制不等同于严格的单帧在途栅栏。此实验可能降低吞吐和流畅度，也仍不能阻止其他进程重选，不能先承诺有效。

此前整段原生 one-shot 已因重选而重播，且用户反馈更差；不要重复把它作为未经检验的新方案。任何下一次试验应同时比较回弹、动画总时长、快速连点延迟和能耗。
